# AGENTS.md

Wear OS round-screen Go (围棋) app, single module `:app`, pure Kotlin + Jetpack Compose for Wear, no GMS deps. Screen logic lives in `MainViewModel.kt`; one Activity (`MainActivity.kt`) with Compose screens under `ui/`. The `game/` package is pure Kotlin with no Android imports.

## Commands

```bash
./gradlew :app:testDebugUnitTest  # the only verification; tests in GameLogicTest.kt + BoardViewportTest.kt
./gradlew :app:assembleDebug
./gradlew :app:assembleRelease    # R8 minify on; signed only if keystore props exist
```

CI: `.github/workflows/build.yml` (unit tests + debug/release APKs as artifacts, GitHub Release on `v*` tags, optional signing via the `KEYSTORE_*` secrets). Release paths: pushing a `v*` tag publishes an official Release; a manual `workflow_dispatch` publishes an official Release when its `tag` input is filled (creates the tag at the dispatched commit, replaces the assets if that Release already exists) and the rolling `ci` prerelease when it is left empty — the two are mutually exclusive, so a manual run never both tags and rolls. Versioning: the release tag is the single source of truth — the `Resolve app version from the release tag` step derives `versionName` (tag minus `v`, suffix kept) and `versionCode` (`major*10000 + minor*100 + patch`, minor/patch must be ≤ 99 or the code collides with a higher version) and injects them as `-PappVersionName`/`-PappVersionCode` into every Gradle invocation; with no tag the `app/build.gradle.kts` defaults (`1` / `"1.0.0"`) apply. The verify step reads the version back out of the universal APK with `aapt2` and fails the run when it doesn't match the tag — keep that assertion (and the tag→version step) when touching the release steps. It builds with JDK 21 and `platforms;android-37.0` — note the new-style SDK versioning: `compileSdk = 37` resolves to the `platforms;android-37.0` package. Without keystore props AGP emits `app-release-unsigned.apk`, so any script copying the release APK must glob `app-release*.apk`.

No lint/formatting/ktlint task is configured. Requires JDK 17+ and Android SDK (compileSdk 37); SDK path comes from `local.properties` (`sdk.dir`) or `ANDROID_HOME`. Debug builds get `applicationIdSuffix = ".debug"`.

## Engine integration (read before touching `engine/`)

The app drives the **Pachi** Go engine (v12.84, GPL-2.0-or-later) in-process via JNI (`libpachi.so` in `jniLibs/`, prebuilt for arm64-v8a/armeabi-v7a/x86_64) over the **GTP protocol** with Lizzie-style `lz-analyze` extensions, parsed in `PachiEngine.kt`. Protocol is coupled to engine behavior; high-signal invariants:

- **Never send `quit`.** Its handler calls `exit(0)` and would kill the whole app process. A session ends by closing the engine's stdin (EOF); `PachiNative.shutdown()` destroys the session and joins the engine thread. The host harness calls it before `System.exit`, otherwise the JVM hangs at shutdown (the dup2'ed engine pipes keep the process stdio busy).
- **stdio is process-wide**: the bridge dup2's pipes onto fds 0/1/2 per session. `destroy_session` must restore the saved stdio fds *before* joining the demux thread — fd 1/2 are dup'ed copies of the pipe write ends, and pipe EOF never arrives while they stay open (this was a real hang). The app itself never writes to System.out, so it needs no workaround; the host harness repoints System.out at `PachiNative.dupStdout()` via `/proc/self/fd/<n>`.
- **Every GTP command gets one reply** (`=` / `?` prefix), strictly in send order. The engine keeps a FIFO of reply slots (`replyQueue` in `PachiEngine`); fire-and-forget commands occupy a slot too, otherwise a later awaited reply would pair with the wrong command. `lz-genmove_analyze` replies `= ` *immediately* and later prints a `play <coord>` line — that line (not the reply) is the actual engine move and completes the await.
- **Stray writes to the engine pipe**: because stdio is process-wide (dup2 above), anything else in the process writing to fd 1/2 (Skia/EGL logs on the emulator produced `s_glBindAttribLocation: ...` lines, ~50 per session) lands in the same stream and is read line by line. `handleLine` ignores shapes it doesn't know, but the reply pattern is broad, so reply slots carry the command text and any `= <non-empty>` line for a command that only ever replies `= ` (everything except `final_score`) is dropped with a warning instead of consuming a slot. If you add a command whose success reply has a payload, extend `returnsPayload`. The real fix would be running the engine in its own process; the current design cannot separate the fds.
- **lz output format** (pinned by `engine-src/host/SmokeTest`): `info move <coord> visits <n> winrate <‰> prior <n> order <k> pv <coords...>` — **multiple segments per line**, `winrate` is the side-to-move win rate in permille (4849 = 48.49%). Note `pv` **starts with the move itself** (`info move C4 ... pv C4 Q17`), so the parser must not prepend it again. The final `play <coord>` may be `play pass` / `play resign`; the app maps those to sentinel coords `passMove = -1,-1` / `resignMove = -2,-2`.
- **No STOP during genmove**: a bounded search (`kgs-time_settings byoyomi 0 <sec> 1`) ends itself. `stopAndAwait` waits for IDLE; analysis is stopped with `lz-analyze <color> 0`. `play`/`clear_board` while analyzing also stop it (`gtp.c`'s `stop_analyzing`), but the app always stops explicitly first. Measured thinking time is ~0.85× the nominal value (pachi reserves 15% of byoyomi plus lag, `timeinfo.c`): 3 s → ~1.0 s, 10 s → ~8.1 s on the emulator.
- **Position sync is whole-board replay**: GTP has no set-position command, so every request replays `clear_board` + `play ...` (passes included). The engine board can therefore never drift from the app's — same design intent as the old YXBOARD flow. `undo` ×N rebuilds the engine position (equivalent to TAKEBACK). Because every request replays, a session rebuild (`startNewGame`, triggered by a board-size/komi change) is harmless — but `final_score` is *not* a replay, so `endByDoublePass` pushes the position with `syncBoard` first.
- `final_score` after a double pass can still fail with `? too early to pass` (engine judges the position unfinished); the app falls back to local area scoring (`GoBoard.score`). `play pass` in the opening is refused the same way — the UI blocks pass-on-empty-board implicitly since two passes are needed and the engine/game treats a 2-pass empty board as not final.
- **Analysis has three entry points with different lifetimes**: `syncAndAnalyze` is fire-and-forget (must be paired with `stop`/`stopAndAwait`), `analyzeFor` runs for a fixed time and stops itself (used by 提示), `scanAnalyze` stops as soon as the first `info move` report arrives, bounded by `maxWaitMs` (used by 全谱分析). Never make a one-shot path use `syncAndAnalyze`: pachi's `lz-analyze` runs forever, so the phase never returns to IDLE and anything waiting on IDLE (the hint ring, `pendingHint`) never fires. The scan `finally` must restore the engine position under `withContext(NonCancellable)` (same rationale as the old Rapfi flow).
- **A short fixed scan window cannot work**: pachi reports every `0.01 * freq` = 0.5 s of search, but the first report lands 0.7–1.2 s after `lz-analyze` (search startup). The old fixed 600 ms per ply captured nothing (the eval curve stayed empty) — keep `scanAnalyze` waiting for the first report instead of a fixed delay, and remember `handleInfoMoveLine` drops lines while the phase is IDLE, so a report that arrives after the stop is lost too.
- The engine thread is `threads=1` with `tree_size=16,max_tree_size=64,max_mem=96` (MiB) — sized for watches. joseki is explicitly disabled in the JNI bridge (`disable_joseki()`): the no-DCNN UCT build `die()`s when `joseki19.gtp` is missing.
- Data files (`patterns_mm.gamma/.spat`, `opening.dat`) ship in `assets/engine/common/` and are extracted to `filesDir/engine` (the session workDir, `chdir`'d in `start()`); missing patterns degrade gracefully to plain Monte Carlo (warning only).

Rebuilding the engine is covered in `engine-src/README.md` (zero upstream patches; `build-host.sh` / `build-android.sh`, NDK per-ABI source copies because pachi's Makefile builds in-tree; `llvm-strip --strip-debug`, never `--strip-all`). `engine-src/host/` is the desktop-JVM harness (`SmokeTest` 8 scenarios green, `Repro` single-step debugger); run it **before** touching Android builds. `engine-src/pachi-src/` is a gitignored clone of pasky/pachi at `617986f4`.

## Go rules (`game/GoBoard.kt`, pure Kotlin)

Chinese area scoring (数子): stones + surrounded empty points count, komi added to White. Self-capture (suicide) is illegal; simple ko is enforced by comparing the post-move board hash against the position before the opponent's last move (`hashes` list, rebuilt on undo by replaying). Passes are `Move(x=-1,...)`; two consecutive passes end the game. `GoBoard.score(komi)` is the local fallback scorer; the engine's `final_score` overrides it when it answers. **Known trap in `neighbors()`**: `buildList { ... size ... }` — the lambda receiver is a `MutableList`, so a bare `size` reads the list under construction, not the board (corner points got empty neighbor lists and were misjudged as suicide). Capture `val n = size` first.

Forbidden-move/Renju logic does not exist in this branch; `winLine` is gone. Add capture/ko/scoring tests to `GameLogicTest.kt` (a real ko needs the surrounding stones to leave the capturing stone exactly one liberty — see the `koBoard()` helper there).

## Board rendering and review mode

`BoardViewport` holds the pure view math (`minScale(size)` fits the whole board incl. corner stones into the round screen, `MAX_SCALE` 3, `DEFAULT_SCALE` 1) and is unit-tested in `BoardViewportTest` for 9/13/19: at every scale in range, any intersection — including the four corner points — can be panned to the screen centre. Keep `BoardViewport` free of Compose types so the tests stay JVM-only. Star points are per-size (`starPoints(size)` in `GoBoardView.kt`).

The hint ring pulse is a finite `Animatable` (`rememberHintPulseState`) — do not replace it with an infinite transition (keeps the frame clock idle between interactions). The hint point comes from `bestMoves` **or** the primary `pvLines` entry: `lz-analyze` never emits the `play <coord>` line that fills `bestMoves`, so the PV first move is the only source. The hint's analysis must be time-bounded (`PachiEngine.analyzeFor`) or the ring never appears.

Move numbers are drawn from `state.visibleMoves` (the move list), so they must be skipped when `state.colorAt(m.x, m.y) != m.color` — otherwise captured stones leave a ghost number on the empty point.

Floating chrome (back button + bottom arc) sits on a 48dp minimum touch target, i.e. a 96px box around a 36px visual at density 2. Measured at 454×454: back `[74,20]-[170,116]`, undo `[40,304]-[136,400]`, redo `[103,350]-[199,446]`, pass `[179,366]-[275,454]`, hint `[255,350]-[351,446]`, menu `[318,304]-[414,400]`. Board intersections under those boxes are either swallowed or trigger the button while the chrome is visible (it auto-hides after 3.2 s). When scripting taps, pick points outside these rects — on 9/13-line boards a tap near the arc silently lands on a button instead of playing a stone.

In-game thinking readout: `GameScreen`'s `ThinkingReadout` shows `胜率 p · 首选 x,y` while the engine searches (data from the already-flowing `pvLines`, throttled by `PV_PUSH_INTERVAL`, hidden with the auto-hidden chrome). Candidate badges A/B/C reuse the same `pvLines` (top `analysisLines` routes).

## Rotary (crown) input

Three paths, all in `GoBoardView`; keep them consistent — zoom direction lives in exactly one place (`applyRotary`): (1) standard rotary via `onRotaryScrollEvent` + `requestFocusOnHierarchyActive()`; (2) mouse-wheel crowns (OPPO OWW251 `oplus_crown`) become pointer `Scroll` events (`PointerEventType.Scroll`); (3) fallback `View.setOnGenericMotionListener` for wheels Compose doesn't consume. `WHEEL_STEP` 0.09 with ±8 cap — measured ~25 events/s on OWW251. On-device diagnosis via streaming `adb logcat` started *before* the action (the watch's small log buffer floods with PV lines; dump-after looks like dropped logs).

## Navigation and the in-memory game

The board is never cleared by navigation — only `startGame`/`clearBoard`/`flipColors` touch it. `backFromAnalysis()` returns to the game whenever analysis came from the game *or* `canResumeGame()`; do not make analysis exit unconditionally `toMenu()`. Changing board size or komi in settings rebuilds the board/session (`sessionKey = boardSize to komi` in `MainViewModel.ensureEngine`).
